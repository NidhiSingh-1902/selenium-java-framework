Framework Flow & Architecture

A complete walkthrough of how the three layers connect, what happens when a test runs, and why the React-specific patterns exist.

Three-Layer Architecture

The framework is split into three layers. Each layer has exactly one job. Click any layer to see its files and responsibility.

C
Chrome Browser + SauceDemo
ChromeDriver 150  ·  https://www.saucedemo.com

ChromeDriver translates WebDriver JSON commands into native Chrome DevTools Protocol (CDP) calls. The browser opens, navigates pages, fills forms, clicks buttons, and returns results — all controlled by the framework layers above.

WebDriverManager (a Maven dependency) automatically downloads the correct ChromeDriver version that matches your installed Chrome — no manual driver setup needed.

The rule that keeps it clean: Tests only talk to Page Objects. Page Objects only talk to BasePage. Nothing skips a layer. This means when a locator changes on a page, you fix it in one place — the Page Object — and all tests that use it automatically get the fix.

What happens when you run mvn test

From the moment you hit Enter to the moment the result prints — every step the framework takes.

1
Maven
Maven reads pom.xml and compiles
Maven downloads dependencies (Selenium, TestNG, Log4j) from Maven Central if not already cached, then compiles all .java files in src/main and src/test.
2
Maven Surefire + TestNG
Surefire plugin hands control to TestNG
Maven Surefire finds testng.xml (configured in pom.xml) and passes it to the TestNG engine. TestNG reads all 8 <test> blocks and builds a list of every test method to run.
3
TestNG + BaseTest
@BeforeMethod — Chrome opens
Before every individual test method, TestNG calls @BeforeMethod in BaseTest. This creates a fresh ChromeDriver instance, maximises the window, and navigates to the SauceDemo login page.
@BeforeMethod
public void setUp() {
    driver = new ChromeDriver();         // fresh browser per test
    driver.manage().window().maximize();
    driver.get("https://www.saucedemo.com");
}
4
Test class
The test method runs — Arrange
The test calls its helper (e.g. loginAndOpenCart()). This creates Page Object instances and calls their methods to reach the right starting state.
// Inside CartTest.cartPageLoadsTest()
CartPage cart = loginAndOpenCart();
// helper does: login → addToCart(0) → goToCart()
5
Page Object → BasePage → Selenium
Page Object translates actions into Selenium calls
Each page method uses inherited helpers from BasePage. For example, goToCart() calls jsClick(cartIcon) then wait.waitForUrlContains("cart.html"). BasePage sends the actual WebDriver commands to Chrome.
// ProductsPage.goToCart()
public void goToCart() {
    wait.waitForVisible(cartIcon);
    jsClick(cartIcon);                        // → ChromeDriver click
    wait.waitForUrlContains("cart.html");    // → polls until URL changes
}
6
Test class
Assert — verify the outcome
Back in the test method, Assert statements check that the outcome matches expectations. A passing assertion does nothing. A failing assertion throws AssertionError, which TestNG records as FAIL.
Assert.assertTrue(cart.isPageLoaded(),
    "Cart page should load");
Assert.assertEquals(cart.getPageHeading(), "Your Cart",
    "Heading should say Your Cart");
7
TestNG + BaseTest
@AfterMethod — Chrome closes
Whether the test passed or failed, @AfterMethod in BaseTest always runs and calls driver.quit() — closes the browser and frees the ChromeDriver process. Every test gets a clean slate.
@AfterMethod
public void tearDown() {
    if (driver != null) driver.quit();  // always runs, even on test failure
}
8
Surefire
Report written to target/surefire-reports/
TestNG emits results to Surefire. A .txt summary and .xml file are written for each test class. Maven prints the final summary: BUILD SUCCESS (0 failures) or BUILD FAILURE (with failure count).
parallel="methods" thread-count="2" in testng.xml means TestNG runs 2 test methods at the same time within each suite. Each gets its own browser instance from @BeforeMethod. The driver field in BaseTest is a ThreadLocal so the two threads never share the same browser.

Page Object Model — How It Works

Page Object Model (POM) is the core design pattern. It separates WHERE elements are (the page class) from WHAT to verify (the test class).

Without POM

Locators and Selenium calls are scattered across test files. When a button ID changes, you search through every test to find all 12 places that reference it.

With POM

Each page's locators live in one class. When a button ID changes, you fix it in one place — the Page Object — and all tests that use it are automatically fixed.

How @FindBy and PageFactory work

When a Page Object is created with new CartPage(driver), the constructor calls super(driver) which calls PageFactory.initElements(driver, this). This scans every field annotated with @FindBy and wraps it in a lazy proxy.

// @FindBy just declares the locator — the element is NOT found yet
@FindBy(id = "checkout")
private WebElement checkoutButton;

// The element is only searched in the DOM when you USE it
public void clickCheckout() {
    jsClick(checkoutButton);   // ← driver.findElement(By.id("checkout")) happens HERE
}
Why lazy? If Selenium found all elements at construction time, any element not yet on the page would immediately throw NoSuchElementException. The lazy proxy re-finds the element each time it is accessed, so it always gets the current DOM node.

How BasePage provides shared behaviour

All 8 page classes extend BasePage. This gives every page access to the same helpers without copying code. When type() or jsClick() needs an improvement, you fix it once in BasePage and every page gets it.

// BasePage.java (simplified)
public class BasePage {
    protected final WebDriver  driver;
    protected final WaitUtils  wait;
    protected final Logger     log;

    public BasePage(WebDriver driver) {
        this.driver = driver;
        this.wait   = new WaitUtils(driver);
        PageFactory.initElements(driver, this); // ← wires @FindBy fields
    }
}

// CartPage.java — inherits everything above automatically
public class CartPage extends BasePage {
    @FindBy(id = "checkout") private WebElement checkoutButton;

    public CartPage(WebDriver driver) { super(driver); }

    public void clickCheckout() {
        jsClick(checkoutButton);                      // inherited
        wait.waitForUrlContains("checkout-step-one"); // inherited
    }
}

How BaseTest manages the browser

// BaseTest.java (simplified) — every test class extends this
public class BaseTest {
    private ThreadLocal<WebDriver> driverPool = new ThreadLocal<>();

    @BeforeMethod
    public void setUp() {
        WebDriver driver = new ChromeDriver();  // new browser per test
        driver.manage().window().maximize();
        driver.get("https://www.saucedemo.com");
        driverPool.set(driver);
    }

    protected WebDriver getDriver() { return driverPool.get(); }

    @AfterMethod
    public void tearDown() {
        if (getDriver() != null) getDriver().quit(); // always close
        driverPool.remove();
    }
}

Why React needs special handling

SauceDemo is a React single-page app. Three standard Selenium behaviours silently fail on React pages. Here is exactly why, and what the framework does instead.

Problem 1 — Clicking buttons

// Standard Selenium click
element.click();   // ✗ Fires a WebDriver synthetic click
                   //   React's event system may not respond
                   //   Cart badge stays at 0, button label doesn't change

// Framework fix
jsClick(element);  // ✓ Fires a native DOM click via JavaScript
                   //   React's delegated event listener always catches it
Why does this happen? React 17+ moved event delegation from individual DOM nodes to the root container. WebDriver's element.click() dispatches a synthetic event at the element level, which can miss React's root-level listener. A direct JavaScript click fires at the DOM level and is always caught.

Problem 2 — Typing into form fields

// Standard Selenium type
element.clear();               // ✗ Clears the DOM value
element.sendKeys("John");     //   but React's internal state stays empty
                               //   Clicking Continue → "First Name is required"

// Framework fix — typeReact()
var setter = Object.getOwnPropertyDescriptor(
    window.HTMLInputElement.prototype, 'value').set;
setter.call(element, "John");  // ✓ Uses the ORIGINAL native setter
element.dispatchEvent(          // ✓ Fires 'input' event that React's
    new Event('input', { bubbles: true })); //  onChange handler catches
Why does this happen? React overrides the native input.value setter to track changes. element.clear() bypasses React's override and resets the DOM without telling React. The framework uses Object.getOwnPropertyDescriptor to get the original native setter (before React patched it), then dispatches a bubbling input event so React's onChange fires and its state syncs.

Problem 3 — Stale element references

// After jsClick("Add to cart"), React re-renders the button node
// The old WebElement reference points to a REMOVED DOM node

// ✗ Using a stored reference — throws StaleElementReferenceException
wait.until(ExpectedConditions
    .textToBePresentInElement(button, "Remove"));

// ✓ Framework fix — waitForTextInElement(By locator, text)
//   Re-finds the element fresh on every retry using the CSS locator
By nth = By.cssSelector(".inventory_item:nth-child(1) .btn_inventory");
wait.waitForTextInElement(nth, "Remove");  // always gets the live node
Why does this happen? When React updates its virtual DOM and reconciles it with the real DOM, it may replace a button node entirely (even if it looks the same visually). The old WebElement reference now points to a detached node — accessing it throws StaleElementReferenceException. Passing a By locator instead of a WebElement to the wait re-runs driver.findElement() on each retry, always getting the current live node.

Quick reference — which method to use

SituationUseNot
Click any button or link in SauceDemo jsClick(element) element.click()
Type into checkout form fields typeReact(field, "value") type(field, "value")
Type into login form (not React-controlled) type(field, "value") either works here
Wait for button text to change after cart action waitForTextInElement(By, "text") waitForTextInElement(element, "text")
Wait for page navigation waitForUrlContains("cart.html") Thread.sleep(2000)
